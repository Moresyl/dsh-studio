这个外壳到底做了什么

harness 是一个能在你机器上执行 shell 命令的命令行工具。这里大部分工作，都是在认真对待这件事：守着它、 把它圈住、不让它上网。

进程守护你还没察觉，它已经重启完了

harness 崩溃后会带着递增退避重新拉起，而不是原地死循环。外壳每 10 秒还会通过 HTTP 探一次活，连续三次没反应就回收重开 —— 从外面看，卡死的服务和已经死掉的服务长得一模一样。

进程隔离没有任何进程能活过窗口

每个子进程都会被加入 Windows 的 job object，或者 POSIX 的进程组。关掉外壳会把整棵树一起收走， 包括那些用普通 kill 会被丢成孤儿、还占着端口的孙子进程。

对外暴露只听回环，端口策略安全可控

harness 默认以 --port 0 启动，外壳再把内核分配的端口读回来；也可以保存 1024–65535 的固定端口，冲突会在 Node 启动前明确提示。它始终只绑定 127.0.0.1，不会监听其他地址。

开箱没有前置条件要你先去读

机器上没有 Node.js？外壳会替你取一份运行时、校验好、放在应用旁边，然后再把 harness 本身装上。第一次启动只是按一个按钮，不是读一页说明。

插件市场就在窗口里

搜 npm registry、看清楚这个插件干什么、装上、随时开关 —— 不用开终端，也不用自己手动重启 harness。

接管扫码把会话交给手机

对着窗口扫一下，就能在自己的网络里用手机接着往下做。配对码一次性、两分钟过期，而 harness 本身始终不离开回环 —— 在局域网上监听的是另一个独立网关。

核对校验和

每个 release 都带一份 SHA256SUMS.txt， 覆盖该版本的所有文件，由构建它们的同一条流水线写出。 

sha256sum -c SHA256SUMS.txt --ignore-missing
Get-FileHash .\DSH.Studio_*_x64-setup.exe

更新包带签名

每个安装包和归档旁边都有一份分离签名。应用会用编译进二进制的公钥先验签再决定是否升级， 被改过的文件会被拒掉而不是装上。

构建过程你能看

安装包由公开的 GitHub Actions 流水线从打了 tag 的提交产出，不是谁从自己笔记本上传的。 流水线文件 和每一次运行的日志都可以查。
